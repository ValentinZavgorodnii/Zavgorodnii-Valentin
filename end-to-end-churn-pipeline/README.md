# E-commerce Churn Prediction & Promo Optimization Pipeline

**Author:** Valentin Zavgorodnii

End-to-End решение для прогнозирования оттока клиентов и оптимизации маркетингового бюджета. Проект охватывает полный цикл разработки: от ручного конструирования признаков (Feature Engineering) и строгой кросс-валидации во времени до деплоя ML-модели в изолированный Docker-контейнер с микросервисом на FastAPI.

---

## Описание задачи и бизнес-контекст

В транзакционном e-commerce (на примере датасета Olist, Бразилия) доля разовых клиентов достигает **99.54%** — большинство покупателей совершают одну покупку и не возвращаются.

**Цель проекта:** Разработать модель классификации для выявления клиентов, которые с высокой вероятностью не совершат покупку в следующие 90 дней, и внедрить алгоритм определения оптимального порога (Threshold) для рассылки промокодов с целью удержания.

Проект фокусируется не только на максимизации метрики ROC-AUC, но и на поиске баланса между стоимостью промокода (Penalty) и ожидаемой прибылью от удержанного клиента (Reward).

---

## Архитектура данных (Feature Engineering)

Для предотвращения Data Leakage (утечки данных) пайплайн спроектирован с использованием концепции **Point-in-Time (срез на момент времени)** со скользящим окном:

- **Историческое окно:** Данные строго до даты отсечки для генерации профиля клиента.
- **Окно таргета:** Факт наличия покупки в следующие 90 дней (целевая переменная).
- **Лаг-признаки (Lag 90d):** Расчёт динамики покупок и трат пользователя за последние 3 месяца перед датой отсечки для определения вектора активности.

### Спроектированные бизнес-метрики

| Признак | Описание | Бизнес-смысл |
|---------|----------|--------------|
| `recent_spend_ratio` | Доля недавних трат от общего LTV | Снижение → сигнал к оттоку |
| `installment_burden` | Отношение суммы заказа к количеству платежей | Высокая нагрузка → риск оттока |
| `purchase_intensity` | Интенсивность покупок во времени | Снижение интенсивности → потеря интереса |
| `delivery_delay` | Фактическая задержка логистики | Задержки → негативный опыт |
| `cancellation_rate` | Доля отменённых заказов | Высокая доля → недовольство |

## Математика и моделирование

Для обеспечения робастности модели проведена обширная настройка и сравнение алгоритмов.

### 1. Валидация
Применён строгий Out-of-Time сплит. Обучение происходило на данных до 01.06.2018. Кросс-валидация реализована через `TimeSeriesSplit` (5 фолдов) для учёта сезонности и хронологического порядка.

### 2. Алгоритмы
Проведено прямое сравнение градиентных бустингов CatBoost и LightGBM.

### 3. Оптимизация гиперпараметров
Тюнинг выполнен с помощью **Optuna** (100 итераций) с использованием байесовского поиска и логарифмических шкал для скорости обучения.

**Победитель:** `LightGBMClassifier`

### Метрики качества

В условиях сильного дисбаланса классов (доля оттока ~0.5%) ключевой метрикой является **PR-AUC** (Precision-Recall AUC), которая честно отражает способность модели находить редкий класс.

| Метрика | Значение |
|---------|----------|
| **CV ROC-AUC (TimeSeriesSplit)** | 0.7627 |
| **Финальный ROC-AUC (отложенный тест)** | 0.7719 |
| **Финальный PR-AUC (отложенный тест)** | **0.9981** |

PR-AUC = 0.9981 показывает, что модель практически идеально идентифицирует уходящих клиентов, минимизируя количество ложных срабатываний и пропусков реального оттока.

## Экономическая эффективность (Business Value)

Модель оптимизировалась под кастомную функцию прибыли:

$$Profit = (TP \times Reward) - (FP \times Penalty)$$

где:
- **Reward = 1500 руб.** — LTV удержанного клиента
- **Penalty = 200 руб.** — стоимость промокода

> *Примечание:* В расчётах использованы условные значения (рубли), демонстрирующие методологию оптимизации порога. В реальном проекте необходимо подставить актуальные LTV и стоимость удержания для конкретного бизнеса. Важно сохранить соотношение Reward/Penalty — именно оно определяет оптимальный порог вероятности.

### Результаты оптимизации порога

| Параметр | Значение |
|----------|----------|
| **Оптимальный порог отсечения** | **0.01** |
| **Ожидаемая прибыль кампании** | **241,075,700 руб.** |
| **False Positives (FP)** | 719 |
| **False Negatives (FN)** | 5 |
| **Размер тестовой выборки** | 161,556 клиентов |

### Интерпретация результатов

- **FP (719):** Это VIP-клиенты с `purchase_intensity` в 2 раза выше среднего. Отправленный промокод будет воспринят как бонус — безопасная и полезная ошибка.
- **FN (5):** Модель пропустила всего 5 реально ушедших клиентов. Потерянная прибыль: 5 × 1500 = **7,500 руб.** — ничтожно на фоне прибыли кампании.

## Интерпретация факторов (SHAP)

Модель не является "чёрным ящиком". Ниже представлен анализ влияния признаков на решение модели об оттоке.

### Глобальная важность признаков

![Топ факторов оттока](graphs/Топ%20факторов%20оттока.png)

**Топ-5 признаков, определяющих отток:**

1. **`customer_city`** — География. Логистика в Бразилии сильно зависит от региона.
2. **`total_spent`** — Чем больше клиент тратит, тем ниже риск оттока.
3. **`tenure_days`** — Давние клиенты лояльнее.
4. **`purchase_intensity`** — Частота покупок. Снижение интенсивности → риск оттока.
5. **`avg_review_score`** — Довольные клиенты уходят реже.

## Продакшен и деплоймент (Docker + FastAPI)

Пайплайн инкапсулирован в production-ready микросервис.

### Архитектура сервиса

```
┌─────────────────────────────────────────────────────────────┐
│                    Docker Container                         │
│  ┌───────────────────────────────────────────────────────┐  │
│  │                   FastAPI Server                      │  │
│  │  ┌─────────────────────────────────────────────────┐  │  │
│  │  │  POST /predict                                  │  │  │
│  │  │  - Валидация через Pydantic                     │  │  │
│  │  │  - Приведение категорий к справочнику           │  │  │
│  │  │  - Предсказание вероятности оттока              │  │  │
│  │  │  - Возврат: churn_probability + send_promo      │  │  │
│  │  └─────────────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────────────┘  │
│                                                             │
│  ┌───────────────┐  ┌────────────────────────────────────┐  │
│  │ churn_model   │  │  categories_dict.pkl (кэш гео)     │  │
│  │ .pkl          │  └────────────────────────────────────┘  │
│  └───────────────┘                                         │
└─────────────────────────────────────────────────────────────┘
```

### Технические решения

| Компонент | Решение | Обоснование |
|-----------|---------|-------------|
| **Веб-фреймворк** | FastAPI | Асинхронность, автодокументация, Pydantic-валидация |
| **Категориальные признаки** | `categories_dict.pkl` | Предотвращение Data Drift при одиночных запросах |
| **Контейнеризация** | Docker (python:3.12-slim) | Лёгкость, воспроизводимость |
| **Точка входа** | Uvicorn | ASGI-сервер для продакшена |

### Инструкция по локальному запуску

1. **Клонируйте репозиторий:**
```bash
git clone <URL_репозитория>
cd end-to-end-churn-pipeline
```

2. **Соберите Docker-образ:**
```bash
docker build -t churn-api .
```

3. **Запустите микросервис:**
```bash
docker run -p 8000:8000 churn-api
```

4. **Тестирование:**
Откройте в браузере `http://127.0.0.1:8000/docs` для доступа к Swagger UI. Отправьте тестовый JSON-профиль клиента и получите вероятность оттока (`churn_probability`) и решение о выдаче промокода (`send_promo`).

### Пример запроса к API

```json
{
  "recency_days": 45.0,
  "tenure_days": 120.0,
  "total_orders": 5,
  "total_spent": 350.0,
  "max_installments": 3,
  "avg_review_score": 4.2,
  "min_review_score": 3.0,
  "avg_delivery_delay": 2.5,
  "max_delivery_delay": 5.0,
  "cancellation_rate": 0.0,
  "customer_state": "SP",
  "customer_city": "sao paulo",
  "avg_spent": 70.0,
  "purchase_intensity": 1.25,
  "lag_90d_orders": 2,
  "lag_90d_spent": 150.0,
  "recent_spend_ratio": 0.43,
  "installment_burden": 116.67
}
```

### Пример ответа

```json
{
  "churn_probability": 0.6125,
  "send_promo": true
}
```

## Резюме проекта

1. **Feature Engineering** — ручное конструирование признаков (лаги, гео, RFM-производные).
2. **Моделирование** — сравнение алгоритмов, байесовская оптимизация, TimeSeriesSplit.
3. **Интерпретация** — SHAP-анализ и Error Analysis.
4. **Бизнес-ценность** — кастомная метрика прибыли, оптимизация порога.
5. **Деплой** — FastAPI + Docker, готовность к продакшену.

**Ключевой результат:** Модель прогнозирует отток с ROC-AUC **0.7719** и PR-AUC **0.9981**, оптимизирована под максимизацию прибыли (**241 млн руб.**) и пропускает всего **5 ушедших клиентов** на выборке из **161 тыс. человек**, что подтверждает высокую точность идентификации уходящих клиентов в условиях сильного дисбаланса классов.
